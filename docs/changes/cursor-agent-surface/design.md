# Cursor agent surface: design

## Approach

Cursor joins `rune run` as a sixth tool in the existing adapter set: one `Surface::Cursor` variant, one row in each table, and one module with the argument builder and the parser. It uses the same process request, owned-argument filter, and failure type as the other tools. The alternative was a generic "JSON print tool" adapter driven by config. It lost because each tool differs in prompt transport, access flags, and error shape, and the owned table is the security boundary, which config must not widen.

## Structure

- `src/cli/surface/cursor.rs`: `BOOLEAN_OPTIONS` and `OWNED_OPTIONS` hold the owned flags, including `--plugin-dir`, because a plugin can add tools. `keep_allowed` then keeps only the flags in `KEPT_OPTIONS`, `-e` and `--endpoint`, and drops every other profile argument, because `cursor-agent` accepts options that its help does not list and because `--api-key` would put the key in `ps`. Its warnings name a flag or a position, never a value. `check_access` refuses a read-only run when the `cli-config.json` in `config_dir` sets `approvalMode` to `unrestricted`. `config_dir` resolves the directory as `cursor-agent` does: `CURSOR_CONFIG_DIR`, then `$XDG_CONFIG_HOME/cursor`, then `$HOME/.cursor`, reading the launch environment before rune's own. A kept flag without a plain value is dropped, because commander takes the next token as the value whatever it is. `args` builds the argument list from the invocation. `prompt_input` puts the system prompt in front of the prompt. `invoke` sends that text on standard input, and `parse` reads the last result object. `prepare_clean_state` returns the configuration error when `CURSOR_API_KEY` is missing. `sandbox_hint` decides whether standard error shows the Keychain failure of a sandboxed process, and `with_sandbox_hint` puts the hint in front of that standard error.
- `src/cli/surface/mod.rs`: the `Surface::Cursor` variant, `from_tool("cursor")`, the name, the table dispatch, the `prepare_clean_state` and `process_request` match cases, and the `invoke_surface` dispatch. The filter uses `drop_whole`, because Cursor has no generic config channel, and passes its result through `keep_allowed`. `check_access` dispatches the access check, and `run/mod.rs` calls it before the tool starts, so a refusal is a configuration error with exit 2.
- `src/cli/launch/mod.rs`: `cursor` in `KNOWN_TOOLS`, and `default_binary(name)`, which maps `cursor` to `cursor-agent`. Both `resolve_tool` and `list_tools` call it, so the list cannot disagree with the launch. `BUILT_IN_PROFILES` holds the `fable@cursor` profile, which selects the built-in route `fable-cursor` (`claude-fable-5-1-high`). Cursor needs this table because it names each Fable effort level as its own id, so no tool-neutral `fable` route can serve it. `resolve_profile` checks the config first, then this table, and `profile_names` merges both for the missing-profile error and the tool list. The built-in routes move into one `BUILT_IN_ROUTES` table, which both the lookup and the unknown-route error read. `model_args` puts `--model <id>` in front of the profile arguments of a Cursor launch and records the pair in `ResolvedLaunch::model_args`. `rune run` strips that exact prefix, because it passes the model itself, so no owned-argument warning fires for a model that rune generated.
- `src/cli/run/mod.rs` and the `run` help text: the supported-tool message and the examples name Cursor.

The argument list for a run is `-p --output-format json --workspace <repo> --trust`, then `--mode ask` or `--force --sandbox enabled`, then `--model <id>` when a model is set, then the kept profile arguments, in the same order as the other tools. The prompt goes on standard input with the system prompt in front of it.

For a clean run the process request sets `HOME` to the clean root and `CURSOR_CONFIG_DIR` to `<root>/.cursor`. The API key stays in the environment. `has_api_key` checks the launch environment, which holds profile `env` values, before rune's own, because the child gets the launch environment last.

## Risks

- **A new Cursor flag widens access.** The allow-list covers it: a profile keeps only the account and endpoint flags, so a new or unlisted flag never reaches the tool. The owned table stays for its value-aware warnings. The bypass table test has Cursor rows for owned and unlisted flags.
- **Ask mode is a CLI rule, not a kernel boundary.** `cursor-agent` enforces it: every live read-only run that asked for a file wrote nothing, including one under a copied `unrestricted` config. The model still lists Shell, Write, and StrReplace as its tools under ask mode. `check_access` refuses `unrestricted` as defense in depth, because it is the one approval mode that would run such a call without asking if the enforcement failed. A read-only run cannot add a kernel sandbox, because `--sandbox enabled` without `--force` still asks for approval, and print mode cannot answer. The ADR records this limit.
- **The JSON shape changes.** Cursor does not document `usage`. The parser makes `usage`, `subtype`, and `is_error` optional. A line without `type: result` or with a non-string `result` is not a result object. An empty or missing `result` fails as an empty reply.
- **The sandbox hint misfires.** The hint matches the certificate-store text, or "Authentication required" only while `SANDBOX_RUNTIME` is set. Outside the sandbox, a real missing login gets no hint.
- **A clean home drops the owner's Cursor hooks.** `~/.cursor/hooks` holds the owner's shell guard. A clean run loses it by design, like every other clean run. Workspace-write clean runs rely on Cursor's own sandbox.
