# Design

The research, the vendor protocol table, and Astra's schematics live in the workshop under `docs/specs/2026-09-27-rune-hooks/`. This file holds what the code needs.

## Runtime

```text
harness event, stdin JSON
        |
rune hook run --harness H --native-event N --plan PATH [--on-failure deny]
        |
the budget clock starts here, before the cover record, the payload, or the plan is read
if H is claude and the payload carries Grok's camelCase keys: exit 0, log, stop
read the compiled plan at PATH, the path install wrote into the registration
(a user config newer than the plan is a warning on stderr, never a reload)
plan missing or unreadable -> the registration's --on-failure decides: deny where H can block
check argument against the payload's event name
normalize -> HandlerPayload v1
        |
for handler in plan[H][event], serial, ordered:
    a legacy part covers it: skip only while every cover condition holds now;
    a doubt runs the handler, and a cover that holds skips it even past the deadline
    deadline = min(handler.timeout, remaining - reserve - 150 ms stop allowance)
    none left -> failure by policy, no spawn
    spawn exec, payload on stdin, RUNE_HARNESS RUNE_EVENT RUNE_HANDLER_ID RUNE_REMAINING_MS
    on expiry: SIGTERM, 10 ms grace, SIGKILL to the process group
    parse one JSON Result (unknown fields refused, v must be 1); empty stdout or anything
    else is failure by policy (warn: log; deny: Result deny)
    a replacement input from a `rewrites: true` handler becomes the effective input
    for the handlers after it; from any other handler it is a failure by policy
    continue_turn outside turn.finish is a failure by policy; a deny outranks every effect
    gate: stop on deny   collect: merge context in order, keep a deny   passive: ignore effects and input
        |
dispatcher failure (mismatch, decode, plan) -> strongest policy among subscribed handlers
encode Result for H and N -> stdout JSON, exit 0
```

## Modules

- `src/cli/hook/config.rs`: `HooksConfig { defaults, events, handlers }` from the `hooks:` key of the user config. `Handler { id, exec, events, order, timeout_ms, on_failure, requires, per_harness, rewrites, adopts }`. Validation names the field: empty events, unknown event or capability, `deny` on a non-gate event (a `per_harness` override included), a rewriter after a guard. The rewriter check runs per harness and native event on the policy each harness resolves, so a guard that is `deny` on one harness only orders the rewriters there.
- `src/cli/hook/plan.rs`: the compiled plan per harness and event, with clamped timeouts. `rune hook list` and `--events` print it.
- `src/cli/hook/events.rs`: `Canonical` (eight), `native(harness)`, `mode`, `default_budget`, `cap(harness)`. Extensions as `Extension { harness, name }`.
- `src/cli/hook/payload.rs`: decoders for Claude, Codex, Grok, Gemini, Antigravity into `HandlerPayload`, `raw` kept. Release 1 registers Claude and Codex; the others decode for the tests and the later change.
- `src/cli/hook/run.rs`: the dispatcher above, spawning through `src/cli/process`.
- `src/cli/hook/encode.rs`: Claude and Codex encoders for every effect; the other harnesses' tables so an unsupported effect is reported.
- `src/cli/hook/adapters/`: built-in handlers that call the existing executables with their native payloads and translate to `Result`: `author-identity`, `dcg`, `git-ai`, `rtk`, `lint-on-write`, `session-capture`, `turn-checkpoint`, `tmux-status`, `jj-guards` (the worktree, agent isolation, and VCS internals parts as one handler). Each adapter declares `adopts`, the registration pattern of the entry it replaces. The dcg adapter hands dcg every shell tool as one Claude `Bash` call: `Bash`, Gemini's `run_shell_command`, Antigravity's `run_command`, and Codex's `shell` (an argument list), `shell_command`, and `exec_command` (its `cmd` field). The [Codex hooks reference][CODEXHOOKS] matches `exec_command` as `Bash` (read 2026-10-24), so the other names are the shapes a decoded payload can still carry.
- `src/cli/hook/install.rs`: render one entry per subscribed event into Claude `settings.json` and Codex `hooks.json`; inventory the tables; adopt matching predecessor entries in Claude `settings.json` and Codex `hooks.json`, name a tool's entry in Codex `config.toml` by the line of its command value, from the TOML parser's spans (that file also holds the trust state, so rune never rewrites it); keep every legacy dispatcher entry, and record in a cover file beside the generations each handler whose whole command a part of that entry runs, with the entry's slot in the table install writes; write the manifest section; print the Codex trust step; `--check`.
- `src/cli/hook/legacy.rs`: the legacy dispatcher shapes, the known content of the dispatcher script, the parts folder of an event and the names every locale sorts one way, the first part's shape (an optional `-x` or `-f` guard on the program its one final `exec` line runs), `$HOME` expansion outside single quotes and the refusal of every other expansion, the text a counted line may hold and the glob characters it may not, the system `sh` by canonical path, the shebang check of a direct entry, the caps on a folder scan, and the bounded non-blocking read every cover file goes through. It parses no loop and no other line.
- `src/cli/hook/cover.rs`: the cover record per harness and event, the header check that binds a record to its name, the keys a covered hook and its group may carry, the firing environment (`HOME`, `PATH`, `CLAUDE_CONFIG_DIR`, and the variables that change how `sh` reads a script), what each built-in adapter runs on a harness and event, the whole-command match by canonical program path and exact arguments, the per-firing cache of tables, script, folders, shell words, and the bytes of parts left, and the check the dispatcher runs before it skips a handler. It refuses every record for Codex.

## Data

- Handler payload: `{"v":1,"harness","event","native_event","session_id","turn_id","cwd","transcript_path","model","tool":{"name","id","input","response"},"prompt","stop_active","raw"}`.
- Result: `{"v":1,"effect":"pass|deny|continue_turn","reason","input","context":[]}`.
- Plan: `{harness: {native_event: {canonical, mode, budget_ms, handlers: [{id, exec, timeout_ms, on_failure, rewrites}]}}}`.
- Plan generation: the plan narrowed to one harness and native event, in `hooks/plans/<sha256 of its text>.json` under the state directory.
- Manifest `hooks` section per harness: `owned: [{event, registration_hash}]`, `foreign: [{event, source, command}]`, `adopted: [{event, source, command, by}]`, `generations`, the generation paths the registrations name after the last install, `installs`, the count of installs that wrote the manifest, and `retired: [{generation, since, install, days, last_day}]`, each generation no table names with the time and the install count at which the tables stopped naming it, and the number of days on which installs found it unnamed.
- Identity: `user.name` and `user.email` in the jj config of the workspace the session runs in, through `jj config set --workspace`. jj 0.46 keeps one file per workspace under the user's config directory, so a second workspace of the repository never reads it. When colocated, the handler turns on `extensions.worktreeConfig` and writes `git config --worktree`. git-config(1) wants a `core.worktree`, or a `core.bare` that is true, moved by hand first, so with either set the handler writes the shared `.git/config` and says so in its context.

## The registration

Each rendered entry is `rune hook run --harness H --native-event N --plan PATH`, plus `--on-failure deny` when a handler of that event resolves to `deny` and the harness can block it. `PATH` is the registration's own plan generation, made absolute against the install's working directory, because `RUNE_STATE_DIR` may be relative. A harness that starts the dispatcher elsewhere, without `RUNE_STATE_DIR`, or with another `XDG_STATE_HOME` then reads the plan install wrote. The policy in the registration is what a missing, truncated, or deleted generation falls back to. The dispatcher does not compile the config in that case, because the compiled plan stays its only source of handlers (review hit 17 below). A guarded Claude entry also carries `"onFailure": "block"`. The [Claude Code hooks reference][CCHOOKS] (read 2026-10-24) says the field arrived in v2.1.295 and that a failure then "does what exit code 2 does on that event". It covers a hook that cannot start, exits other than 0 or 2, times out, or prints invalid JSON, and it has no effect on `Stop`. The owner's Claude Code is 2.1.309. Codex documents no such field, so its entries carry none.

The stop allowance is 150 ms: the 25 ms poll that notices the deadline, the 10 ms grace, the group kill, and the drain of the pipes, each rounded up to the next poll. With the defaults a `tool.before` handler gets at most 2800 ms of the 3000 ms budget, and its denial leaves before Claude's 3 s timeout even when the handler ignores SIGTERM.

Claude and Codex read the entry's `timeout` as whole seconds, so the plan clamps a budget to the whole seconds of the harness's cap, rounded down, and the entry carries the budget rounded up: the deadline ends inside the rendered timeout, and the rendered timeout never passes the cap. The [Claude Code hooks reference][CCHOOKS] (read 2026-10-25) gives `SessionEnd` hooks 1.5 s by default and raises that budget to the highest per-hook `timeout` in the settings files, up to 60 seconds, so Claude's `SessionEnd` cap is 60 s and 1.5 s is its default. Codex's `SessionEnd` keeps 1 s by default and 3 s at most, the values `codex_trust.rs` hashes.

An entry is rune's when its command, read with shell quoting, starts with a binary named `rune` on any path, then `hook run`, and names the table's harness after `--harness`. So an install from a second build path finds the first one's entry. A known entry is replaced with the one this install renders, and a second known entry on the same event is removed, so each event keeps one dispatcher.

## The dispatcher log

`hooks/run.log` under the state directory gets one block per event: the time, the harness, the native event, `tool NAME`, and one `ID EFFECT` or `ID failed KIND` line per hook. The command, the file, and every reason stay out of it, because a command line can carry a credential and a guard often quotes the line it refused. The hook record holds the rest without text. The file is created with mode 0600, and at 256 KiB it moves to `run.log.1`, so at most two generations remain.

## Install as one step

`install::prepare` reads the manifest and every registered harness table and computes the new tables without writing. A hand-edited owned entry or an unreadable table stops it there. The new plan generations are written first, then `publish` stages each changed table and the manifest beside their targets and renames them in that order. Each staged file has a name no other run uses, from the process id, the clock, and a counter, and it is created new, so two runs never write one file. A staged file whose write or permission change fails is removed at once, so no partial file stays beside its target. Before a rename, the old target is kept beside it as a hard link, or a copy where the file system has no links. When a rename fails, each target already replaced gets its backup back by rename, so a read-only target goes back too, and a target that did not exist is removed again. A restore that fails is named in the error. An install that writes holds an exclusive lock on the directory of every file it may write, the manifest's and each harness table's, from the first read to the last generation deleted, so a second install waits for it. The generations live under the manifest's directory, so its lock covers them. The lock is std's `File::lock` on an empty `.rune-install.lock` in each directory: `flock` on Unix and `LockFileEx` on Windows, so it holds on every platform rune is released for. A `flock` on the directory itself left nothing behind, but Windows opens no directory as a file, and the Windows build took no lock at all (found in review, 2026-10-24). It creates each of those directories before it locks them, so every install that shares a target locks the same directory. Locking the nearest existing ancestor instead let a second install lock the directory the first one created while staging, and both held their locks at once (found in review, 2026-10-24). Each directory is locked once, by its canonical path. A check or a dry run writes nothing and takes no lock. A relative `RUNE_STATE_DIR` once named the state directory both relatively and absolutely, and the second lock waited for the first forever (found 2026-10-24).

A config with no handler still reconciles when an earlier install left a plan generation or an owned entry in the manifest. Install then renders an empty plan: rune's commands go, every foreign command stays, and every generation is recorded as no longer named. With neither, there is nothing to take back, and install writes nothing.

A proof scene keeps the runner's HOME for tools that need it, such as a harness login, so a hook install from a scene would point the live registrations at a plan the runner deletes. The runner writes a marker file into each scene's capture directory, with its own process id and HOME, and names it in `RUNE_PROOF_SCENE`. The capture directory goes when the scene ends, and the marker goes with it. A hook install counts the marker only while the file exists and the process it names still runs, so a shell that carries the variable after the proof installs as usual. With a live marker for its HOME, `rune hook install` fails and names the HOME, and `rune install` reports the hook step as `skipped` with the reason. The check comes before the config is read, so the skip line is the same on every machine.

A table that is a symbolic link, such as a `settings.json` the dotfiles keep, is resolved first, and the file it points to is the one staged and replaced, so the link survives. A replaced file keeps its permission bits, and a new table is created with mode 0600. `table.rs` reads the table's members in file order with `serde_json`'s `RawValue` and writes back only the `hooks` member. Every other member keeps its text and place, and so does every event under `hooks` the install left alone. `serde_json`'s `preserve_order` feature would keep the order too, but it applies to the whole crate. It lets `HashMap` iteration order into every `serde_json::Value` rune prints, so `rune config reference` changed from one run to the next (tried 2026-10-24). Registration hashes are taken over the entry with its keys sorted, so a key order change alone is no conflict.

## Plan generations

Each registration names its own plan generation: the compiled plan narrowed to the registration's harness and native event, in `hooks/plans/<digest>.json`, where the digest is the SHA-256 of the file's text. No install rewrites a generation. An install writes the generations of its registrations before the tables, so a table never names a file that is not there. A registration of the old tables reads the plan it was installed with, byte for byte, while its table changes and for as long as the generation stays. The dispatcher reads a generation only when its bytes hash to the digest in its name. An edit that clears a guard's handlers still leaves a valid plan, and the event would run unguarded, so a mismatch is a plan that does not load, and the registration's `--on-failure` policy answers. `--check` names such a file, and the next install writes it again. An event whose plan did not change keeps its generation, its command, and so its Codex trust, which covers the command. A generation of the whole plan would change every registration's command on every config edit, and Codex would stop running each one until the owner trusted it again.

A generation outlives the tables that named it. The owner runs many Claude and Codex sessions at once. The [Claude Code hooks reference][CCHOOKS] (read 2026-10-25) says "Direct edits to hooks in settings files are normally picked up automatically by the file watcher." Codex loads its hooks once per session. Rune relies on neither: it keeps each generation on disk, because a session that has not reloaded calls the old `--plan` path until it restarts, and "normally" names no case in which the watcher does not. Under `deny`, each guarded call of that session would fail if the file were gone. The limit is that rune cannot read when a running session last loaded its table, so it keeps every generation by the window below, whether or not a session still names it. So the manifest's `retired` list records, for each generation no rune registration names, the time and the install count at which the tables stopped naming it, and the days on which installs found it unnamed. `retire.rs` holds the rules. The manifest is the last file of the step, so an install killed after the tables changed leaves the old manifest. So, before the tables change, install writes the old manifest once more without the record of any generation the old or the new tables name. A record that survives a kill is then never older than the last time a table named its generation, and a kill can only delay a deletion (found in review, 2026-10-24). The step's own manifest drops the same records and gives each generation the old tables name and the new ones do not a fresh record at this install. After publication, install reads every table again, records any other unnamed generation, and counts today for each record once. It deletes a generation only when its record is 14 days old, at least two more installs have run, and installs on 14 different days have found it unnamed. The recorded time decides over the mtime, because a reused generation's mtime moves with each install that names it. A clock set forward ages a record, and quick installs raise the count, but neither adds a day on which an install ran, so the day count bounds the window by real days. The review offered a second rule, 14 days from the later of the record and the last install. The day count is simpler, because it needs no time beyond the record's own, and it still lets a generation go for an owner who installs every day. A generation holds the handlers of one event, so the window costs little disk. An install that fails stops before the cleanup, so its new generations stay unrecorded until the next install records them.

`rune hook install --check` reports a registration whose generation is missing, and the dispatcher answers such a registration with its `--on-failure` policy. That is the limit of the window: a session that runs past the 14 days, two more installs, and 14 install days after the tables stopped naming its generation falls to that policy, a guarded event then denies every call, and a restart loads the current registrations.

The plan used to be one file, and the install published a bridge before the tables: the new plan merged with the old. Review found three ways the merge failed an old guard (2026-10-24). An observer that reused a guard's id replaced the guard. A new rewriter could run after an old guard and hand out an unchecked input. A new passive mode turned the old guard's denial into a log line. Generations remove the merge, so all three are gone.

`rune hook list --write` still writes the whole plan to `hooks/plan.json` for a machine that installs nothing, and `rune hook run` reads that file when no `--plan` names another.

## Ownership of the Claude table

The dotfiles render `~/.claude/settings.json` from a template. Release 1 turns that template into a chezmoi `modify_` script that takes the live file's `hooks` key as is, so rune's entries survive `chezmoi apply`, and declares no hook of its own. The legacy dispatcher entry stays: the owner's parts keep running through it, and install never removes it or asks for its removal.

Install adopts a predecessor only from a command that runs it alone. It reads the command's words with shell quoting, and a tool is the first word's file name, so `~/.local/bin/dcg` names dcg and `/bin/sh -e ~/.local/bin/dcg` names nothing. A command with `;`, `&`, `|`, `<`, `>`, `(`, `)`, `$`, a backtick, or a line break joins, redirects, or substitutes commands, so `$HOME/.local/bin/dcg` is compound too. Such a command, for example `sh ~/.sd/hook PreToolUse && /owner/check-policy`, stays whole. Install warns that it runs the predecessor with other commands, and the owner splits it by hand. The turn-checkpoint adapter runs `~/.config/just/claude/turn/checkpoint`, else `~/.sd/claude/turn/checkpoint` for a home the dotfiles have not moved yet. A part that matches a handler changes none of this: the handover of a direct entry is the predecessor's alone.

A rune handler does not run on an event where a registered hook on that event already runs the same program. The legacy dispatcher is such a hook: `sh ~/.config/just/hook <Event>`, the older `sh ~/.sd/hook <Event>`, or `sd hook <Event>`. Install decides nothing for good. It keeps every handler in the generation, so the registration, its command, and its Codex trust stay put when the parts change. For each handler whose whole command the first part of the folder runs, it writes one record to `hooks/cover/<harness>-<event>.json` beside the generations: the entry and its slot, the script, the folder, the part, the part's `exec` words, and what the adapter runs. The output names the handler and the part as `covered:`. `rune hook run` reads that file at each firing and skips the handler only while every condition still holds: the record names this harness and event, the entry stands at its slot with that command, with no key beyond the ones rune reads, under no matcher or `*`, the script holds the content install accepted, the `sh` on `PATH` is `/bin/sh`, no variable that changes how `sh` reads a script is set, the part is still the first of its folder with the same shape and words, the handler about to run is the recorded one by command and policy, and the adapter still runs that command on this harness and event. A failed or unreadable condition runs the handler, so a doubt costs a double run and never a missing hook. A part removed after install brings its handler back at the next firing, with no install. The hook record names a skipped handler with its part in `skipped`. Only the first part can cover, because the dispatcher stops at the first part that exits non-zero, so a later part runs only when every part before it succeeds, and no file rune reads says whether one did. On the owner's layout this covers tmux-status on `Stop` and `UserPromptSubmit`, and turn-checkpoint runs twice on those events. A dispatcher entry timeout that kills the run before the first part is the one gap left: the harness ends a run, and no file rune reads says so.

Install and the dispatcher read only what they can be sure of, and read text only the way the shell reads it. A counted line holds printable ASCII alone, no carriage return and no backslash, every quote closed on its line, and its words split on space and tab. A counted file ends its lines with plain line feeds. Any other byte covers nothing, because the shell may read it as a word rune did not see. The dispatcher script counts when its content, without comments and blank lines, is the live `~/.config/just/hook` rune knows. The older `~/.sd/hook` counts under the same content, because the repository holds no other version of it. Nothing parses the loop. The shell in front counts only when its word is `sh` or `/bin/sh` and resolves as the shell resolves it, on `PATH` for the bare name, by canonical path after symlinks, to `/bin/sh`. `bash` and `zsh` read startup files such as `BASH_ENV` and `~/.zshenv`, which rune never reads, so they count as nothing. A file named `sh` anywhere else, first on `PATH` or named by path, counts as nothing, and so does a shell with an option. The dispatcher runs each part with a bare `sh`, so the `sh` on the `PATH` of the install and of each firing must resolve to `/bin/sh` too, or nothing is covered. An entry with no shell in front needs an executable script whose first line is exactly `#!/bin/sh`. A counted word holds no unquoted `*`, `?`, or `{`, and no `[` paired with a `]` in the same word, because the shell expands such a word by the files it matches or by its braces, and rune reads a literal. A `[` alone is the test command of a guard and stays. Whether `/bin/sh` expands braces was not checked, so `{` is refused as if it did. A counted word expands `$HOME` and `${HOME}` outside single quotes and nothing else: any other `$`, a backquote, or a `~` at the start of an unquoted word covers nothing, because the shell reads the environment or the password file there and rune would read a literal. Before this, `"$HOME/.local/$OTHER/claude-tmux-status"` canonicalized `$OTHER` as a folder of that name (found 2026-10-25). The parts are the `*.sh` entries of the event's folder, no dot names, and only the first of them can cover, because the dispatcher stops at the first part that fails. Which part is first depends on the shell's locale unless every `*.sh` name is two ASCII digits, a hyphen, lower-case ASCII letters, digits, and hyphens, then `.sh`, with no two names on one number: such names sort one way under every collation. Any other name, or two names on one number, makes the folder cover nothing, and install names the entry. The first part must be a regular file in the shape: without comments and blank lines, an optional `[ -x "<path>" ] || exit 0` or `[ -f "<path>" ] || exit 0` on the program its one final `exec` runs, and nothing else: no second `exec`, no `if`, no `nohup`. A later part needs no shape and is not read. A folder counts only up to 16 entries of any kind, dot names and other suffixes included, and one install scan or one firing reads at most 256 KiB of parts in all, each under 64 KiB. Past either cap the folder covers nothing, and install says so. The owner's folders hold two or three parts of a few lines each, so the caps leave room. The brief measured 2.1 s for 10,000 accepted parts of 64 KiB, which is about 0.2 ms per part of that size, so a scan at the byte cap takes about 1 ms. A guard whose program is missing makes the part inactive, and an inactive part covers nothing, because the dispatcher would skip it. The `-x` guard is read with `access(2)` for execute permission, as `[ -x ]` in `/bin/sh` is, so root and the file's group see what the shell sees. Every check runs at install and again at each firing.

A part covers a handler only when its `exec` words are the whole command the handler's adapter runs on that harness and event: the same shell in front by name, the same program by canonical path after symlinks or by the same bare name, and the same arguments. A bare name and a path are never compared, and a prefix never matches. A `deny` handler, a handler with its own arguments in the config, and a handler whose adapter reshapes the payload off Claude (dcg, rtk, turn-checkpoint, tmux-status) are never covered, because the part would feed its program another input. A handler with `rewrites: true` is never covered either, because its output feeds the handlers after it and a part keeps its output to itself: a covered rtk left dcg checking `git status` while Claude ran `rtk git status` (found 2026-10-25). Install covers nothing under a matcher other than every tool or in a compound line, and warns where a part may then run twice.

The dispatcher reads every field the harness reads. A hook is covered only when its keys are among `type`, `command`, `timeout`, and `statusMessage`, and its group's keys among `matcher` and `hooks`, on Claude and on Codex alike. A key such as `if`, `args`, or `async` changes when or how the harness runs the command, so it means no cover, at install and at each firing. At a firing the dispatcher takes `HOME` from the environment alone, and an unset or empty `HOME` covers nothing. Install and the firing cover nothing while the environment sets a variable that changes how `/bin/sh` reads or runs a script, because rune reads the script and its parts as plain text and that variable makes the shell read something else. The list is `BASHOPTS`, `BASH_COMPAT`, `BASH_ENV`, `ENV`, `EXECIGNORE`, `GLOBIGNORE`, `GLOBSORT`, `IFS`, `POSIXLY_CORRECT`, `SHELLOPTS`, and every name that starts with `BASH_FUNC_`, which is how bash exports a function. The sources are the bash 3.2 manual at `/usr/share/man/man1/bash.1` on macOS, where `/bin/sh` is bash 3.2, and the bash 5.3 manual at `/opt/homebrew/share/man/man1/bash.1` (both read 2026-10-25): `BASH_ENV` is read by a non-interactive shell, `SHELLOPTS` and `BASHOPTS` are imported from the environment at startup, `IFS` splits words, `GLOBIGNORE` and `GLOBSORT` change what a pattern matches and in what order, `EXECIGNORE` changes which files a `PATH` search runs, `ENV` and `POSIXLY_CORRECT` change the POSIX mode, and `BASH_COMPAT` changes the compatibility level. Neither manual names `BASH_FUNC_`. That prefix is the name bash gives an exported function in the environment, which rune did not check against a source in this round, so the match is on the prefix alone and errs toward running the handler. It reads the Claude table under `CLAUDE_CONFIG_DIR` when the variable holds an absolute path, as Claude does, and a relative value covers nothing. When that table is not the file the record names, or the home is not the one install read, nothing is covered. Install reads the table under the home alone and honors no variable, so a harness pointed elsewhere runs every handler. The record's header names its harness and event, and a record copied to another name reads as no cover. The handler about to run is checked against the record too: its command, its `on_failure`, and the adapter's command on this harness and native event, so a handler renamed, given arguments, or moved to an event where the adapter reshapes the payload runs. Every file the cover touches is a regular file under a limit, opened without blocking, or it counts as nothing: 1 MiB for the record, 8 MiB for a table, 64 KiB for the script and each part, and 256 KiB of parts in one firing. The budget clock starts before the record is read. A cover that holds skips its handler even when its checks end past the deadline: the part runs the command either way, and the handler would only run it again, so the record carries the part as `skipped`. A handler the cover does not hold is not spawned past the deadline, and its record carries the `budget` failure. One firing reads each table, the script, each folder, and each shell word once, in a cache the handlers of the event share.

## Codex trust

Codex binds trust to the hook's hash. An entry rune writes is inactive until the owner accepts it in the harness (`/hooks`). The install prints that step, `--check` reports an untrusted rune entry, and a predecessor is adopted only once the rune entry is trusted, so no event goes unguarded in between. A legacy dispatcher entry on Codex covers nothing. Codex loads its hooks and their trust once per session, and rune would read the trust file per firing, so a handler skipped at a firing could be one the session never runs: a session started before the owner trusted the dispatcher runs no part of it. Install writes no Codex cover record, and the dispatcher refuses any record for Codex. The handover of a direct entry, below, still reads the trust. The trust reader treats a `config.toml` that is not a regular file, or is over 8 MiB, as holding no trust, so every rune entry reads as untrusted and the handover keeps the predecessor until the file reads again.

The same rule holds for rune's own earlier entry. A changed plan gives an event a new generation, so its entry gets a new command and a new hash, and Codex skips it until the owner trusts it. Replacing the trusted entry in place left the event unguarded until then (found in review, 2026-10-24). Install now keeps an earlier rune entry that Codex trusts where it stands, records it as owned again, and adds the new entry in a group of its own after it. The trust step names the new entry's position, and `--check` fails until Codex trusts it there. The next install then removes the earlier entry and leaves its group as `{"hooks": []}`, so the new entry keeps the position Codex trusts. Until that install, a trusted pair runs the event's handlers twice, from both generations.

A removal moves every later hook of its group to a lower handler, and Codex keys trust by handler too. Removing rune's earlier entry from a group it shared with a guard Codex trusts moved the guard, and Codex skipped it while `--check` passed (found in review, 2026-10-24). On Codex, install now tries each event's removals first: rune's earlier entry, a duplicate, an entry the plan drops, and an adopted predecessor. It holds every removal that would move a hook Codex trusts where it stands, until no removal moves one. The output names the held hook, the hook it keeps in place, and the step: remove the held hook by hand, then trust the moved hook again in `/hooks`. `--check` reports each held removal, and every hook that is not rune's and that Codex does not trust where it stands, in a group that holds a rune entry or loses a hook. A hook the owner disabled in Codex is the owner's choice, and is no drift.

`codex_trust.rs` checks that trust the way Codex does. The [Codex hooks reference][CODEXHOOKS] says Codex records trust against the hook's current hash and runs no untrusted non-managed hook. Codex keeps it in the user `config.toml` as `[hooks.state."<hooks.json path>:<event label>:<group>:<handler>"] trusted_hash`. The hash is `sha256:` over the sorted JSON of `event_name`, the group's `matcher`, and the one handler's `type`, `command`, `timeout`, and `async` (`hook_hash` in [Codex's discovery code][CODEXDISCOVERY], read 2026-10-24). A recomputation matched the hash Codex stored for the owner's dcg entry. Install reconciles each guarded event twice before it writes: once with every predecessor kept and once with every predecessor removed. It reads the rune entry's trust at its position in the second table, the table that adoption would write. Only an entry Codex trusts there lets the predecessors go. A Codex group that adoption or removal empties stays as `{"hooks": []}` while a later group follows, rune's new group included, because Codex keys trust by position ([codex#49399][CODEX49399]). A predecessor before the rune entry in the same group still moves it to the next lower handler number. Install then keeps every predecessor, says which position the entry would move to, and asks the owner to remove the predecessor by hand and trust the entry again. A predecessor that shares a group with other hooks still moves the hooks after it, and their trust has to be renewed.

The Codex encoder sends `permissionDecision: "allow"` beside `updatedInput`. The Codex hooks reference says "Return `updatedInput` only with `permissionDecision: "allow"`", so without it the rewrite is reported as an error and dropped. The reference does not say whether that `allow` also skips Codex's own approval for the call. The encoder keeps it. The only rewriter is rtk, which the owner keeps in every mode, and the plan validator puts every rewriter before the guards, so the guards judge the rewritten call.
