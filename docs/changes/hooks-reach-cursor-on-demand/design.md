# Design

## Approach

Cursor joins the dispatcher the way Codex did: one more `Harness` variant, a native event per canonical one, a decoder for its payload, and an encoder for its answer. The install treats Cursor's flat table as a group of one per hook: on read every entry is wrapped as `{"hooks":[entry]}`, the one reconciliation runs unchanged (owned entries by their `hook run --harness cursor` command and hash, foreign entries kept in place), and on write the groups are unwrapped again. That keeps ownership, the manifest, the conflict check, and the generation sweep the same code for three harnesses. No adapter adopts a predecessor on Cursor, so the owner's dcg and git-ai entries are foreign entries that stay. The `version` member is added only when the table is actually written, so a check or a dry run never touches it.

The alternative, a second installer for flat tables, was rejected: it doubles the reconciliation and the manifest shape for one harness.

Harness choice is a parameter of the one install: `prepare` takes the registered harnesses to write, and only their tables are opened, locked, or created. An unselected harness keeps its table and its manifest record unopened; its generations come from the manifest, where each harness's record lists the plan generations its entries name (older manifests fall back to the owned entries' `--plan` paths), and count as named before and after, so the sweep retires nothing of its. Removal, `rune hook remove`, is an install of the empty plan into the selected harnesses, the same path an owner with no handlers already takes.

Which harnesses a full install touches is decided by the file system, not by memory (owner, 2026-11-02). `rune install` and a bare `rune hook install` attempt Claude, Codex, and Cursor; a harness whose folder (`~/.claude`, `~/.codex`, `~/.cursor`) does not exist is skipped and reported as skipped, and nothing is made for it: no folder, no table, no lock file. Nothing records a removal, so a later full install puts a harness back as soon as its folder exists, and `rune hook remove` is undone by the next install. A named `--harness` whose folder is missing is skipped and reported the same way. The alternative, a manifest that remembers the harnesses the owner took rune out of, was built and dropped: it made the install's reach depend on history, and the owner's rule is that a fresh machine behaves like the old one.

The per-harness switch is a small file in rune's state directory, because `~/.config/rune/config.yaml` is chezmoi's output. `compile` reads it, drops the switched-off handler from that harness's events, and records the choice in `Plan.off`, so the list, the install, and every dispatcher firing see the same plan. `rune hook on` and `rune hook off` then run the install for the registered harnesses they named, the same work as `rune hook install --harness`, so off means off without a second command (owner, 2026-11-02). The verb's output carries the install's report.

Every writer takes the install's whole lock set in one call, in one order: the state directory, which holds the manifest, the generations, and the switches, and the directory of each selected table, sorted by canonical path (`InstallTarget::lock`). The switch takes that same set up front, before it reads anything, so two switches never read one state and each write its own, and a switch and a plain install never hold one directory each while waiting for the other's; a switch that locked the state directory alone and then asked for the tables could (review, 2026-11-02, round four). The install reads the switches after the lock, not before, so a switch that lands while an install waits is in the plan the install publishes, and the install cannot undo it with a plan compiled earlier. `rune hook list --write` is a writer too: it takes the same set before it compiles and holds it through its publish, since a listing that compiled first and locked around the write alone could overwrite `plan.json` with a plan from before a switch, and a firing with no `--plan` reads that file (review, 2026-11-02, round five). A listing that writes nothing takes no lock. The install reads the switches from the file, so the new state is written first; an install that fails, on a conflict for one, puts the file back exactly as it was before the error returns, its bytes and its mode, or its absence, so the file never says a handler is off while a table still fires it and the owner's own formatting survives a refusal (review, 2026-11-02). The lock is re-entrant per thread, and the `Lock` value is not `Send`: the hold is counted per thread, and a value dropped elsewhere would leave the directory locked.

A table entry an install cannot replace still names the generation it was installed with: Codex keeps a trusted entry until it trusts the replacement, and a session that loaded the old table calls the old path. So the dispatcher reads the switches file beside the generation it runs, at every firing, and leaves a switched-off handler out there too (review, 2026-11-02; the alternative, a switch that fails loudly on Codex until the owner trusts the new entry in `/hooks`, would make off wait on a step the owner may not take for days). The switch's output still carries the install's trust line, so the owner sees the old entry stays. The firing finds the switches beside the plan it was given, anchored to the plan's absolute path as the registration names it and to nothing in the firing's own environment: `switches.json` beside `plan.json`, or beside the `plans/` directory a generation is in, so a registration that names another state directory's plan reads that directory's switches, and a relative plan path is refused rather than resolved in the working directory. The path is read lexically, not canonicalized: a `plans` that is a symbolic link to a directory of another name keeps its name, and the switches sit beside the name the switch wrote them beside, not beside the link's target (round five). The file is read strictly and bounded: a regular file under 64 KiB, UTF-8, both members and no other, version 1, and the path itself is examined, not what it points at, so a symbolic link at the path, dangling or not, is a file that does not read. A missing file is no switch. A file that is there and does not read is treated as a plan that does not read: the firing falls to the registration's `--on-failure` policy and runs no handler, since which handlers the owner turned off is unknown (review, 2026-11-02, round four; the earlier behavior, running the generation as installed, revived a switched-off handler from a trusted Codex entry). The install and the switch refuse such a file too.

The dispatcher's answer to Cursor is always a JSON object, on every path: a handler failure that does not deny, an event no handler subscribes to, and a passive observation of a permission event (`beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile`, `beforeTabFileRead`, `subagentStart`) all encode through `encode_cursor`, and a permission event with nothing to deny answers `{"permission": "allow"}`, because Cursor blocks the tool on a missing or invalid `permission`. Cursor's shell tool is named `Shell` with its command in `tool_input.command`; the dcg and rtk adapters read it as they read `Bash`, so the one guard covers both harnesses. Cursor sends `tool_input` and `tool_output` as JSON strings on some events (`beforeMCPExecution` its params, `postToolUse` its result), so the decoder parses each where it parses and keeps the string otherwise. The postbox hands a posted message to a firing only where the harness takes context on that event (`Capability::supported_on`, and `supported_on_native` for an extension): on Cursor that is `sessionStart`, `postToolUse`, and `postToolUseFailure`, so a message posted before a Cursor prompt waits for the next tool. `postToolUseFailure` has no canonical event, so a handler reaches it as `cursor:postToolUseFailure`, and its context goes into `additional_context` as on `postToolUse`.

`rune hook on|off NAME` routes by the flag before the name: `--provider` always means the staged hook rune, `--harness` always means the declared handler, and a bare name is a handler when a handler declares it, a rune when none does, and a structured error, `hooks.ambiguous_name`, when a declared handler and a staged rune share it.

## Structure

- `src/hooks.rs`: `Harness::Cursor` in `ALL` and `REGISTERED`; `native()` arms for seven events and `None` for `notification`; `can_block` and `Capability::supported` extended; `SwitchedOff`, `Switches` (`is_off`, `turn_off`, `turn_on`), `Plan.off`, `Hooks::compile_with`.
- `src/cli/hook/payload.rs`: the Cursor arm of `decode` (`conversation_id`, `workspace_roots`, `tool_input` and `tool_output` parsed when they are JSON strings, `loop_count`, `generation_id`).
- `src/cli/hook/encode.rs`: `encode_cursor`, always a JSON object on stdout.
- `src/cli/hook/install.rs`: `rendered` without `type` and with `failClosed` for Cursor, `flat_table`, `wrapped`, `unwrapped`, `hooks_of`, `CURSOR_TABLE_VERSION`, `table_path` for `~/.cursor/hooks.json`, `prepare_in` with the selected harnesses, `HarnessManifest.generations`, `recorded_generations`, `table_files`, `named_generations`, and `sweep_generations` over the selected harnesses only, `table_dir_exists` and `present` (the folder rule), `Report.skipped`, `Dispatchers::covered` empty outside Claude.
- `src/cli/hook/table.rs`: `ensure_member`, which appends a top-level member once and leaves a present one's text alone.
- `src/cli/hook/switches.rs`: the file under the state directory, `read_at` (bounded, strict), `harnesses` (name parsing), `route` (`Flag` and `Route`: the flag decides before the name), `switch` (the verb's work under the install's whole lock: the read, the change, the install for the registered harnesses it named, the exact rollback through `Original` when the install fails, and its output), `path_beside_plan` (anchored to the canonical plan path) and `apply` (the switches a firing honors).
- `src/cli/hook/mod.rs`: `InstallTarget` (`select`, `lock`, `install`): the harnesses one install writes, the whole lock set in one order, and the compile and write under it; `install_report` and `switch` both go through it.
- `src/cli/hook/publish.rs`: `Lock` re-entrant per thread (`HELD`) and not `Send`, so the switch's lock covers the install's and a hold never outlives its thread's count; `RUNE_HOOK_LOCK_TRACE`, a test's window on the lock: when it names a file, the process appends `wait <dir>` before each lock wait and `held <dir>` after, so a test that holds a lock knows when its child has reached the wait instead of sleeping.
- `src/cli/hook/mod.rs`: `Mode { check, dry_run, remove }`, `install_tables`, `install_report` with the requested harnesses filtered by the folder rule and the skipped ones reported, on the nothing-to-do path too (`Report.nothing`), `compile_switched`, the `off:` line in `render_plan`.
- `src/cli/hook/run.rs`: `dispatcher_failure` and `unregistered` answer through `encode`, so Cursor gets an object on both paths; `run` applies the switches beside the plan before it dispatches, and falls to the registration's policy when the switches file is there and does not read.
- `src/cli/hook/encode.rs`: `cursor_permission_event`, the passive `allow` on a permission event.
- `src/cli/hook/adapters.rs`: `is_shell_tool` (`Bash`, `Shell`, `shell_command`, and the other harnesses' names), `postbox_at` asking `Capability::supported_on` per event.
- `src/hooks.rs`: `Capability::supported_on(harness, event)`, the per-event form of `supported`; `supported_on_native(harness, name)` for an extension, and `CURSOR_TOOL_FAILURE`.
- `src/cli/add/mod.rs`: `stages_kind`, whether a staged hook rune carries a name.
- `src/cli/mod.rs`: `HookAction::Install { harness }`, `HookAction::Remove`, `--harness` on `On` and `Off`, `hook_switch`, which routes through `switches::route`.
- `src/result.rs`: `HookSummary.skipped_harnesses`.

## Data

- `~/.cursor/hooks.json`: `{"version": 1, "hooks": {"<event>": [{"command", "timeout", "failClosed"?}]}}`. rune's entry has no `type` (Cursor's default is `command`) and no `matcher`; `timeout` is in seconds, rounded up from the event's budget as for Claude and Codex.
- `<state>/hooks/switches.json`: `{"version": 1, "off": {"<handler id>": ["cursor", ...]}}`, mode 0600, removed when nothing is off; read strictly, as a regular file under 64 KiB with exactly these two members and this version.
- `Plan.off`: `[{"harness": "cursor", "handler": "jev"}]`, serialized only when non-empty, so earlier generations still read.
- The Cursor dispatcher answer: `{"permission": "allow" | "deny", "user_message"?, "agent_message"?, "updated_input"?}` on `preToolUse`; `{"continue": true | false, "user_message"?}` on `beforeSubmitPrompt`; `{"followup_message"}` on `stop`; `{"additional_context"}` on `sessionStart` and `postToolUse`; `{}` otherwise.
- The firing record's `unapplied`: `["context"]` and the like, the effects the hook asked for that the answer could not carry on the event (`context`, `message`, `denial`, `continuation`, `input`), each one also the subject of a "reported, not applied" line on stderr. Two places drop: `merge` discards a passive event's denial and replacement input before the encoder sees them and returns what it discarded, and the encoder collects its own drops in `Answer.unapplied` where it prints the line (`unexpressed`, `steering`), among them a replacement input on any event but `tool.before`, the one event with a field for it. `settle_unapplied` in `run.rs` stores both on the record of every hook whose result asked for the effect. The member is absent when nothing was dropped, so absent means everything the hook asked for reached the harness, and older records and every reader of the record, the jev client's Vale join among them, keep the members they had (review, 2026-11-02).

## Limits

- Cursor documents no numeric default timeout and no cap; rune writes the event's budget and relies on it.
- Context on `stop`, `preCompact`, and `sessionEnd` has no field in Cursor's answer, so the plan and the firing report it as not applied there, on stderr and in the record's `unapplied`; `sessionStart`, `postToolUse`, and `postToolUseFailure` take it.
- Cursor's `ask` permission is not used: a gate answers allow or deny.
- Cursor's cloud agents do not load user-level hooks; the install writes the user table only.
- Nothing is adopted on Cursor, and dcg stays separate (owner, 2026-11-02): the hand-written dcg entry in `~/.cursor/hooks.json` is left exactly as it is, a foreign entry beside rune's, and rune does not take it over. With rune's dcg handler also on, a shell command is guarded twice; that is the owner's choice per harness, through `rune hook off dcg --harness cursor`.
- A switch leaves the handler out of the plan and rewrites the table, and a firing of an earlier generation reads the switches too, so a session that loaded the earlier table stops running the handler at its next firing; what a switch cannot stop is a handler already running.
- The folder rule reads only the folder's existence: a harness that is installed elsewhere, or whose folder exists without the harness, is treated by its folder.
- The dcg and rtk adapters answer on Cursor's `preToolUse` for `Shell`; the owner's own dcg entry on `beforeShellExecution` is a separate hook with its own answer.

## Risks

- A Cursor permission hook with no output blocks the tool. `encode_cursor` emits an object on every path, and the test `cursor_answers_in_its_own_shape_and_never_in_silence` holds it there.
- A rewrite of the Cursor table could lose a foreign entry or the `version`. The install test seeds the owner's live shape and asserts every foreign command, its order, `failClosed` on the guard, and `version` after two installs and a removal.
- An install into one harness could retire another's generations. The test installs a smaller plan into Cursor alone and asserts Claude's table, manifest record, and generation stay.
- A switch could silently change which events are guarded. The plan names every switched-off handler, and the install test asserts `failClosed` leaves Cursor's `preToolUse` while Claude's `onFailure` stays.
- A switch could report off while an entry still runs the handler: a Codex entry trusted where its replacement is not. The test `a_codex_switch_holds_where_codex_keeps_the_trusted_entry` trusts the entry, switches, fires the kept command, and asserts the handler did not run.
- Two switches could lose one another's change, or a refused install could leave the state and the tables apart. `a_switch_waits_for_the_lock_before_it_reads_the_state` holds the lock while a switch starts and changes the state under it; `a_switch_the_install_refuses_leaves_the_state_as_it_was` refuses the install on a conflict and asserts no switch stayed; `a_refused_switch_puts_the_switches_file_back_as_it_was` asserts the file's bytes and mode after a refusal.
- A switch and an install could each hold a directory the other waits for. `a_switch_takes_the_install_s_whole_lock_set_in_the_install_s_order` holds a table's directory, starts a switch, and asserts it holds no state lock while it waits, then runs an install beside it and asserts both end.
- An install could publish a plan compiled before a switch it waited on. `an_install_reads_the_switches_under_its_lock` holds the lock while an install starts, lifts the switch under it, and asserts the published plan runs the handler; `a_listing_that_writes_compiles_under_the_install_s_lock` does the same to `rune hook list --write` and reads `plan.json`. Both, and the lock-order test, wait on the child's lock trace, not on a sleep: the child has reached its lock wait when the parent goes on.
- A `plans` link, or a link at the switches path, could hide the switches. `a_firing_finds_the_switches_beside_a_plans_link_by_its_name` fires through a `plans` that links to a directory of another name and asserts the switched-off handler stays off; the policy test adds a dangling `switches.json` link and asserts the deny.
- A switches file that does not read could revive a switched-off handler, or hold a firing. `a_switches_file_that_does_not_read_follows_the_registration_s_policy` fires a guarded registration over a malformed file, a wrong version, an unknown member, and a FIFO, and asserts a deny and no handler run, in time.
- A firing could read another state directory's switches, or a checkout's. `a_firing_reads_the_switches_beside_its_plan_whatever_the_state_directory_says` fires with `--plan` under one state directory and `RUNE_STATE_DIR` at another, and with a relative plan path.

## Commands

The delta names roles: the owner chooses, the dispatcher answers, the installer writes. This table carries the commands and flags that implement each requirement, as `rune hook --help` prints them.

| Requirement | Command and flags | Files | Diagnostic ids | Exit status |
|---|---|---|---|---|
| Cursor Hears The Dispatcher | `rune hook run --harness cursor --native-event <e> --plan <p>`, written by the install | `~/.cursor/hooks.json` | none | 0; a denial is in the answer, not the status |
| Cursor's Table Keeps Every Other Entry | `rune hook install`, `--check`, `--dry-run` | `~/.cursor/hooks.json`, `<state>/hooks/manifest.json` | `hooks.conflict` | `--check` exits 1 on drift |
| The Owner Chooses Harnesses | `rune hook install --harness cursor`, `rune hook install --harness claude,codex --check`, `rune hook remove --harness cursor [--dry-run]`; `rune install` and a bare `rune hook install` attempt all three and skip a harness without its folder | the chosen tables whose folders exist, only | `hooks.unknown_harness`, `hooks.unregistered_harness` | as the install; a skipped harness is a `skipped:` line, not an error |
| The Owner Switches A Handler Per Harness | `rune hook off jev --harness cursor`, `rune hook on jev --harness cursor`, `rune hook off jev` (every harness), `rune hook list` | `<state>/hooks/switches.json`, then the chosen registered harnesses' tables | `hooks.unknown_handler`, `hooks.ambiguous_name` | 0; the install's report follows the switch line |
| A Staged Hook Rune Keeps Its Verb | `rune hook off <Name> --provider claude` (unchanged; `--provider` always means the rune) | `.rune` | `hooks.unknown_handler` when `--harness` names no declared handler | 0 |
